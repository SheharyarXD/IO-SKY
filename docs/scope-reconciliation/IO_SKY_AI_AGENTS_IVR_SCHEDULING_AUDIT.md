# IO SKY — AI Agents, Receptionist, IVR, Telephony and Scheduling Audit

Prepared 15 October 2026. Read with `AUDIT_METHOD_AND_SOURCE_LIMITS.md` and the CSV matrix. Physical PDF page numbers include covers. This report makes no production data changes.

## The eight-agent claim

Master SRS §19.5, PDF pp118–119, names **ten** examples: AI Support Agent, AI Sales Agent, AI Receptionist, AI Voice Agent, AI Operations Agent, AI Project Assistant, AI Document Assistant, AI Reporting Agent, AI Compliance Assistant, AI Executive Assistant. Its wording is “Examples include, but are not limited to”. The full-text search found each of the six non-communication assistant names only once, in that list. Four communication agents recur in §§17.2, 17.6 and 17.11. The four are therefore not merely optional registry labels.

The September Finalised Scope PDF p3 calls “eight other” agents baseline while excluding them from that milestone. Ten total minus Receptionist/Sales is a possible reading of eight; it is not a separate SRS list of eight functional definitions. The supplied SRS contains no eight individual agent specifications. This corrects the premise without denying actual AI platform obligations.

## Shared architecture and what exists

Two executable model-call paths were located: AI Scan analyst (`server/_core/aiScanScoring.ts`) and inbound lead qualifier (`server/leadEvaluation.ts`). Both use the shared LLM wrapper and registry/prompt/execution helpers. This is source evidence, not proof that two agents have successfully run live. The report explicitly leaves first funded live output pending.

`ai_agents`, `ai_prompt_versions`, `ai_executions` and `ai_usage` support common governance. The registry table does not fully model every field required by §19.17: tools, knowledge sources, supported modules, responsible owner, version and escalation/organization authority need further mapping. The generalized permission-aware context, knowledge retrieval and multi-session conversation recovery required by §§19.8, 19.20–19.21 are not established by a scan draft or an execution log.

One runtime can host multiple distinct agent capabilities. Each capability still needs its own business function, scoped inputs, approved prompts, permitted tools, output validation, audit and human-escalation policy. Ten independently deployed services are not required. A registry entry or admin page is insufficient.

```mermaid
flowchart LR
  Channels[Authorized portal or voice channel] --> Runtime[Shared AI runtime]
  Runtime --> Gate[User and agent permission gate]
  Gate --> Context[Permission-scoped context and knowledge]
  Context --> Tools[Approved booking CRM report or support tools]
  Tools --> Approval[Human approval or escalation when required]
  Approval --> Audit[Execution history and notifications]
```
